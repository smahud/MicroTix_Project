## Findings

### SCOPE-001 — P1: resolution for one migration session replays as success for a different session

**Evidence:** `backend/domains/customers/views.py:572–584` scopes `identity_conflict_resolve` to `group_id` only, using `resource_is_uuid=False`, although the route and handler also take `migration_id`. The handler obtains that session at line580 and writes through `resolve_conflict_group(session, ...)` at line584. `backend/domains/customers/services.py:572–575` derives group ID solely from sorted usernames; lines578–611 find groups tenant-wide, not per migration. Lines637–650 store `MigrationAccountDecision` **per session** and update that session's state. Database uniqueness is `(session, discovery_object)` (`customers/models.py:264–267`).

**Concrete flow:** authenticated principal P in tenant T resolves group G for migration session A with key K/body B, resulting in two A decisions and cached204. The same P/T/K/B resolving G for migration B hits the same `identity_conflict_resolve:T:G` record and returns204 at `common/idempotency.py:112–117`; B's handler never runs, so it gets no decisions. A missing or malformed `migration_id` can likewise receive cached204 without `_get_session`/UUID validation. This is a silent false-success/cross-resource replay within tenant scope, not a claim of a demonstrated cross-tenant data leak.

**Minimum correction:** make the resource include canonical migration/session UUID plus the opaque group ID. Validate every structured identity component before replay; preserve username/group exact semantics. Do not introduce a framework or change network mutation behavior. Review compatibility of the old group-only key shape at the same time.

**Closing acceptance:** authenticated HTTP tests with real domain rows: A→B same principal/tenant/group/key/body gives each session its own decisions and logical response; retry A remains same action. Missing session returns404, malformed parent422 even after an earlier G response is cached; UUID aliases for the same parent share identity. Keep tenant/permission/revocation and full PA-006 regression green. Standalone expected-fail tests were prepared; this sub-reviewer has not run them against PostgreSQL.

### SCOPE-002 — P1: legacy successful SaaS proof keys are bypassed by the new invoice scope

**Evidence:** baseline `PaymentSubmissionView` had `@idempotent("payment_submission")` and therefore old scope `payment_submission:T:`. Candidate `subscriptions/views.py:99–104` adds invoice ID; `common/idempotency.py:155–159,170–194` claims only `payment_submission:T:I` with no old-scope reconciliation. Migration0004 preserves old rows but does not map changed identities. Candidate `subscriptions/views.py:113–125` writes a fresh proof file and a fresh `PaymentSubmission` on every fresh execution. `subscriptions/models.py:155–190` has no constraint preventing a second submission for the same logical old key/invoice. Uniqueness of later platform source-events or state-machine approval does not prevent this duplicate submission/file effect.

**Concrete flow:** before upgrade, P/T/I/K/B successfully uploads proof, creating submission S plus a nonexpired old-scope201 key record. After upgrade, P retries the same URL/key/body. New scoped claim does not see that old record and performs another upload/create; response points to S2 rather than S. An old no-response record with ambiguous effects is also bypassed, so the blanket "legacy record without response → fail-safe409" claim does not cover this changed scope.

**Minimum correction:** add a bounded compatibility/reconciliation policy for changed legacy identities. For a completed old proof record, verify principal and actual submission→tenant/invoice association before safe replay/adoption; never replay invoice A's response to B. For ambiguous incomplete legacy effects, return a truthful safe reconciliation outcome instead of blind creation. Preserve history and business records; do not blindly rewrite scope or drop old rows. Consider old platform-session/UUID-alias scope changes under the same explicit policy.

**Closing acceptance:** real PostgreSQL upgrade-oriented fixture or migration test using the **old scope**, both with completed success and missing response. Exact same actor/tenant/invoice/key/body must not create a second submission/file; different target must never receive old target's response; concurrent legacy retry must be safe; TTL policy explicit. Existing `test_legacy_record_of_other_principal_never_leaks_response` (`test_idempotency_pa006.py:968–989`) uses an unchanged quotation scope, so does not test this defect. Parent's separate race reviewer is preparing a runtime probe; runtime status is not claimed by this author.

### SCOPE-003 — P2: UUID identities inside request bodies are hashed before canonicalization

**Evidence:** `common/idempotency.py:52–54,160` serializes raw request data with JSON key sorting only; it canonicalizes route tenant/resource at lines154–159, not known UUID body fields. For example, `billing/views.py:221–238` assigns a package to a service after `_parse_uuid(body["package_id"])`. Canonical hyphenated and uppercase compact package UUIDs mean the same package to the handler, yet produce different HMAC input, so same logical key retries yield409 rather than replay. Task0010 mandatory work2 explicitly says to canonicalize structured identities before scope/**hash**, while preserving exact-case semantic strings.

**Minimum correction:** normalize only typed, declared structured identity fields for relevant handlers before hashing, while preserving array semantics/order, username/password exact case and real changed-body/file409. Do not globally rewrite arbitrary strings or add a generic schema framework.

**Closing acceptance:** real HTTP test: first assign package via canonical `package_id`, then same key with compact/uppercase alias; both200, same logical response, no second change. Different actual package ID remains409. Apply equivalent known-ID normalization to other affected payloads as appropriate. A standalone expected-fail conformance probe is prepared; this reviewer has not run it.
