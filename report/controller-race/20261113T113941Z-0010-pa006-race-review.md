## RACE-01 — P1: upgrade drops protection for a successful legacy SaaS proof submission

Evidence:

- `backend/domains/subscriptions/views.py:99–104` changes resource from empty (main) to invoice UUID.
- `backend/domains/common/idempotency.py:153–159,171–176,192–194` only claims/looks up the new exact scope; no legacy changed-scope lookup or reconciliation.
- `backend/domains/jobs/migrations/0004_idem_principal_scope.py:9–19,43–54` retains rows unchanged, changing only uniqueness. It claims pending legacy records cannot be blindly reexecuted, although that is true only if the new scope still matches.
- `backend/domains/subscriptions/views.py:113–125` always writes a fresh proof file and new PaymentSubmission when reached.
- `backend/domains/subscriptions/models.py:155–190` provides no domain uniqueness on a logical proof submission; its primary key is fresh UUID.
- `backend/tests/integration/test_idempotency_pa006.py:943–1012` covers expired quotation, a different principal under unchanged quotation scope and TTL platform decision; it never seeds same-principal successful changed-scope proof history.

Concrete flow: before upgrade an authorized owner POSTs invoice A proof using key K. The request commits submission S and cached response under `payment_submission:<tenant>:`. The owner loses the HTTP response. Migration 0004 leaves the record intact. After upgrade the same owner retries same URL, key and body inside seven days. New code computes `payment_submission:<tenant>:<invoice A>`, sees no collision, and executes the handler. It writes another proof and another submission instead of replaying S. This is a new upgrade regression, not the documented safe rejection of old platform decisions.

The old record can also be pending/ambiguous; changed-scope lookup omission would bypass the intended fail-safe in `_replay_or_reject`. The successful-history flow alone is sufficient to establish the defect without inventing an impossible intermediate transaction state.

Impact: duplicate operator-facing payment proof submissions and extra external files during routine upgrade retry; violates stable same-logical-action replay and safe legacy handling. This report does not claim double ledger posting or invoice activation, which have separate state guards.

Minimum correction: define safe changed-scope legacy handling for the same principal and key; resolve a cached response to its actual invoice/tenant before reuse, preserve fresh invoice A/B separation, and fail safely/reconcile ambiguous legacy effects instead of assuming a new logical action. A broad cross-principal fallback or replaying legacy invoice A on invoice B would reintroduce the original defect. No new broker/framework is necessary.

Closing acceptance: seed actual pre-PA006 durable history, then retry on the candidate. Same principal/invoice/key/body returns original submission with count=1 and no second file; target B never receives A's response. Same key changed-body conflicts safely. Missing/ambiguous legacy result cannot create duplicate effects. Prove relevant same-principal UUID-alias/platform changed-scope policies as well and update report claims.

Proposed standalone pytest: `/workspace/scratch/9b9247ab90da/test_pa006_legacy_review.py`. It creates an actual domain submission plus the exact old successful cached scope/response, and POSTs the same key/body/owner to the live DRF route. Expected: original response and one submission. Root owns running it on a private PostgreSQL database and retaining authoritative output. **NOT_RUN by this sub-agent**; runtime outcome must not be inferred from this proposed test file.

## Protocol findings that do not require a redesign

1. The INSERT-first protocol at `idempotency.py:164–196` is coherent for configured PostgreSQL READ COMMITTED. For tenant views the nested atomic block is a savepoint inside `TenantApiView.dispatch`'s outer `tenant_scope`; IntegrityError rollback restores a usable outer transaction before lookup. For platform views the decorator owns the outer transaction. `claim_inserted` is set after successful create, distinguishing a business IntegrityError from a claim collision.
2. Claim, DB handler effects and response persistence share a transaction on the active successful paths. Newly generated in-flight claims do not commit without their responses. This closes a DB commit/response-persistence gap; it does not establish exactly-once filesystem or device effects.
3. `_purge_expired` uses `FOR UPDATE SKIP LOCKED` and bounded claim retry; a race may replay a just-expired record or start a fresh action after deletion. No concrete duplicate within retained new-format same-identity history was found. No TTL stress experiment was run by this reviewer.
4. New suite genuinely coordinates a blocked leader and a follower, checks PostgreSQL activity and checks effects. It now contains the previously missing leader-abort/follower-takeover test and resource route alias test. These close the executor-internal E-P2-1/E-P3-1 evidence gaps at source level, subject to root runtime results. The legacy coverage gap in RACE-01 remains.
5. Decorated tenant handlers already ran in an outer transaction before this change. Inspection found no new active device/network polling wait introduced by adding the savepoint. Most network paths queue existing jobs. Platform approval's newly enlarged transaction surrounds existing DB state changes, not live router I/O.

## Operational and documentation notes (non-blocking observations)

- `0004_idem_principal_scope.py:26–28` describes per-statement partial leftovers. Django's default PostgreSQL atomic migration instead commits or rolls back both operations together. Correct the narrative when documenting recovery; do not imply a required partial-DDL repair.
- New uniqueness permits rows sharing `(scope,key)` across principals. Old application code still queries those columns without principal, so mixed old/new application processes are unsafe after the constraint expansion. State a drain/write-freeze and migration/code rollout order in upgrade notes; no rolling/zero-downtime claim is justified by Add-before-Remove alone. This is a compatibility prerequisite, not an instruction to edit the installer in task0010.
- `PaymentSubmissionView` writes files before database commit. A rollback can leave an orphan file. That behavior existed before PA-006 because tenant handlers already had `tenant_scope`; no new regression is asserted here. Report DB guarantees separately from external-file effects/recovery.
- Handler returns non-2xx without raising would commit a claim without cached response, but current decorated handlers raise for errors. Existing internal note remains a latent helper-contract issue, not an independent current-path blocker.
- Blocking same-key INSERTs wait for leader completion; existing long receipt/proof I/O and worker lifecycle improvements belong to scoped follow-up PA-002/003. No new timeout policy is requested here.
