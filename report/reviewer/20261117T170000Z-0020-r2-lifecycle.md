## REV-1711-01 — guard and domain commit are still separable

`backend/domains/jobs/engine.py:204–212` reads token/epoch/state with a
plain SELECT. Neither that SELECT nor the final call in `scope()` at
line234 holds a job-row lock until domain commit. Merely executing the
read inside `transaction.atomic()` does not serialize a concurrent UPDATE
of the jobs row at PostgreSQL READ COMMITTED. The check also omits lease
expiry and expected active state; the current concrete probe below focuses
on the confirmed reconciliation race rather than asserting extra failures.

The production `run_discovery` unit at
`backend/domains/network/services.py:1350–1375` checks ownership once at
entry, then inserts DiscoveryObject, marks snapshot SUCCEEDED and advances
MigrationSession without another guard or a held ownership lock.
`DiscoverRouterHandler.execute` passes this real guard at
`backend/domains/network/handlers.py:125`.

Deterministic reproduction authored here:
`test_discovery_guard_and_domain_commit_are_atomic_against_reconcile`.
It runs actual discover_router, pauses immediately *after* its real
post-list_accounts object-unit guard, independently expires/reconciles the
job to UNCERTAIN, then resumes the unchanged domain code. The assertion
requires zero new objects and no successful snapshot after ownership loss.
All worker outcomes are captured and the worker has a bounded join.
The instrumentation only schedules the legitimate concurrent operations;
it does not replace a product decision or inject a fake ownership result.

Minimum correction: serialize the current ownership predicate with each
domain unit's commit on the same tenant connection, using the existing
PostgreSQL row/transaction machinery. Maintain short scopes and avoid
holding those locks across network I/O. Recheck lease validity/expected
state consistently; do not substitute another check-then-write window.
Closure: prior stale-before-guard probe plus this guard-to-commit ordering
must preserve state and effect safety, with a database observer proving the
competing revocation is serialized or the domain unit rolls back.

The executor internal report already calls this residual
**CORR-REV-03** and labels it P3/theoretical. The current proof targets the
same mandatory A01 property and a real production path; classifying the
window as theoretical does not satisfy the requirement.

## REV-1711-04 — durable hold can become stale before ownership acquisition

`backend/domains/jobs/engine.py:645–655` computes router_unknown before
`acquire_router_sender` at line668. There is no second durable outcome
check after successful acquisition. A valid executing predecessor passes
the first query; the predecessor may then finish with timeout-after-send,
commit UNCERTAIN and release its advisory lock before the successor's
attempt. That successor obtains the lock and reaches executing/send even
though no predecessor readback occurred.

Deterministic reproduction authored here:
`test_unknown_router_hold_is_rechecked_after_sender_acquisition`.
The first worker sends and waits; the second passes the actual hold query
then waits before actual advisory acquisition. Root releases and joins the
first worker at UNCERTAIN, then releases the second acquisition. The
assertion requires one total send and a held successor. Both real worker
threads use their independent Django connections; all outcomes are
complete and every participant has bounded join/cleanup.

Minimum correction: combine durable outcome validation and sender
ownership in an ordering that cannot use a pre-acquisition snapshot.
Preserve router independence, outcome readback and old-writer safety.
Closing this SELECT-to-lock gap alone must not be represented as proof
that a lost PostgreSQL session means an adapter writer has stopped: the
advisory lock is scoped to a DB session, not the external adapter session.
The current predicate also overlooks an executing predecessor with a
still-valid lease after hard crash/DB-session loss. Those are boundaries
of the existing A03 obligation, not permission for a new orchestration
framework.

## REV-1711-09 — exact evidence limits

The new signal tests do improve evidence: SIGINT idle/blocked-I/O, signals
during an active barrier, and assertions that a queued second job remains
unclaimed. However `backend/tests/drain_handlers.py:37–49` implements
the supposed second DB unit as `_ = ctx.payload`, with only envelope
progress writes before/after; it has no cooperative domain effect to
observe. The older fast DB handler also performs no DB effect. Keep this
distinction explicit when mapping A08 to evidence.

`_LongPhaseHandler` at
`backend/tests/integration/test_jobs_lifecycle_pa002.py:1136–1161` renews
progress every0.3s. It tests repeated cooperative phases, not a single
valid long-running production adapter phase. Actual backup calls
`adapter.create_backup` after progress, then does not heartbeat until the
call returns (`backend/domains/backups/service.py:184–232`).
`HEARTBEAT_S=10` is declared but unused by the worker. A backup phase whose
duration exceeds LEASE_S=30s can therefore be reconciled despite its
documented backup budget1800s. This reviewer did not execute that long
phase counterexample and does not label it a runtime-confirmed failure.

The new crash-after-domain test at
`backend/tests/integration/test_jobs_lifecycle_pa002.py:1265–1312`
explicitly simulates loss by expiry+reconciliation while a Python thread
waits; it does not kill a process after the domain commit. Separate
SIGKILL coverage exists for the I/O test. Source/readback evidence should
retain that distinction.
