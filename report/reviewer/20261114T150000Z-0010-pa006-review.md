## 3. Analisis eksaktis per dimensi (A–G)

### A. Kebenaran protokol konkuren — LULUS (dengan 2 catatan laten)

**Mekanisme yang diverifikasi** (`backend/domains/common/idempotency.py`):

1. **(1) Duplicate effect dicegah.** Klaim tunggal `INSERT ... ON CONFLICT ON CONSTRAINT uq_idem_identity DO NOTHING RETURNING id` (idempotency.py:90–100). PostgreSQL memaksa konkuren same-identity menunggu keputusan transaksi pemilik klaim pada unique index; hanya satu INSERT mengembalikan baris. Yang kalah menerima `None` → SELECT existing dengan identitas lengkap (idempotency.py:104–110) → replay respons atau 409 beda-body. Tidak ada jalur dua eksekusi handler untuk satu identitas.
2. **(2) Unique-violation 500 dicegah.** `ON CONFLICT ... DO NOTHING` menelan konflik unik; penantang *menunggu* (bukan error) lalu mendapat no-row + SELECT segar (READ COMMITTED — snapshot per statement, SELECT setelah winner commit membaca baris terkomit). Loop 3-attempt (idempotency.py:89, 113–115) menutup race kecil TTL-cleanup antara INSERT dan SELECT ulang.
3. **(3) Replay-buta record tanpa respons dicegah.** `existing.response_status is None` → 409 aman (idempotency.py:179–186); migrasi 0004 mempurge kelas pra-protokol; protokol baru tidak lagi menghasilkan kelas ini pada jalur aktif (lihat poin transaksi di bawah).

**(a) View tenant — klaim+respons+efek commit BERSAMA.** `TenantApiView.dispatch` (common/views.py:101–119): `initial()` (auth/permission/step-up) → `tenant_scope` (common/tenant_context.py:33–53 — membungkus `transaction.atomic()` + GUC RLS) → handler. Decorator `transaction.atomic()` (idempotency.py:167) berjalan **di dalam** transaksi tenant_scope → savepoint. UPDATE respons (idempotency.py:196–199) terjadi dalam savepoint yang sama dengan efek domain; commit final terjadi pada keluar `tenant_scope` → **tidak ada jendela "efek terkomit, klaim/respons belum"**. Penantang same-key menunggu unique index hingga transaksi terluar commit.

**(b) View platform — atomic decorator adalah transaksi terluar.** `PlatformApiView.initial` (subscriptions/views.py:145–151) hanya auth (401/404 generik); decorator atomic terluar; `decide_platform_submission` membuka `tenant_scope` internal (subscriptions/services.py:416) yang menjadi savepoint **di dalam** transaksi decorator → efek tenant-RLS (submission/audit/outbox/source-event) + klaim + respons 204 tetap satu commit. ✓

**(c) Exception setelah claim → rollback seluruh.** Exception di handler menembus atomic decorator (savepoint rollback) → menembus atomic tenant_scope (rollback transaksi penuh) → klaim hilang bersama efek; ApiError ditangani `handle_exception` **setelah** context transaction keluar (dispatch common/views.py:113–116). Jalur platform: atomic decorator adalah terluar → rollback langsung. Retry key semula mengklaim bersih — dibuktikan tes `test_fail_before_db_commit_rolls_back_claim_then_retry_succeeds` (klaim=0 pasca-422; retry 201).

**TTL-delete di dalam protokol** (idempotency.py:170–171): urutan statement seragam antar request (delete→insert→view) — konsisten dengan klaim laporan keputusan 4; delete+insert lintas-request pada row expired berbeda tidak membentuk siklus lock yang bisa saya konstruksi dari pembacaan kode.

**Catatan laten (REV-INT-002):** cabang `if isinstance(response, Response) and 200 <= response.status_code < 300` (idempotency.py:195) — handler yang **mengembalikan** (tanpa raise) Response non-2xx akan membuat klaim terkomit **tanpa** respons → same-key same-body berikutnya masuk cabang 409 "klaim ambigu" secara **permanen** (sampai TTL 7 hari), melanggar semangat packet butir 4 ("jangan menjadikan same-body sebagai idempotency_conflict permanen"). **Tidak ada call site saat ini yang memicunya** — diverifikasi: grep `status=status.HTTP_4|status=4xx` pada semua `backend/domains/*/views.py` mengembalikan nol kecocokan; semua jalur galat memakai `raise ApiError`. Koreksi minimum disarankan: perlakukan Response non-2xx seperti exception (rollback klaim) atau simpan eksplisit dengan kebijakan tertulis.

**Catatan ops (REV-INT-006):** tidak ada timeout aplikasi pada penantangan klaim — request konkuren menunggu sepanjang durasi transaksi winner (tes sendiri memakai `JOIN_TIMEOUT_S = 90`). Bukan bug korektness (semantik §5 replay terpenuhi via menunggu), tetapi risiko latensi HTTP yang perlu disadari ops.

### D. Kompatibilitas/legacy migrasi 0004 — LULUS (1 catatan)

Diverifikasi `backend/domains/jobs/migrations/0004_idempotency_identity.py`:
- **Backfill deterministik**: seluruh baris dimaterialisasi dulu (`order_by("-created_at", "-id")`, baris 49–53) sebelum mutasi; parsing `operation:tenant:resource` format protokol lama (`git show HEAD:backend/domains/common/idempotency.py` — `scope = f"{operation}:{tenant_part}:{resource}"`, tenant_part raw tanpa kanonikalisasi — alias uppercase memang menghasilkan scope berbeda pada protokol lama, sesuai bukti masalah packet). Parse tidak pernah *raise* → migrasi tidak dapat gagal karena data lama rusak (salah bentuk → hapus + statistik).
- **Dedupe**: identitas canonical pasca-normalisasi → dipertahankan record terbaru; record tanpa respons dipurge lebih dulu sehingga yang bertahan selalu punya respons (baris 57–84). Kebijakan konsisten dengan docstring & §5 kelas cache ≤7 hari; business uniqueness domain tidak tersentuh.
- **Ordering constraint**: AddField×3 (nullable) → RunPython backfill → AlterField NOT NULL → RemoveConstraint lama → RemoveField `scope` → AddConstraint `uq_idem_identity` (baris 112–159). Urutan benar: kolom diisi sebelum NOT NULL; constraint baru dipasang setelah dedupe → tidak ada data lama yang melanggar constraint baru; constraint lama dihapus sebelum kolom derivatnya.
- **Reverse jujur**: re-add kolom `scope` NOT NULL pada tabel berisi baris ditolak PostgreSQL → reverse penuh hanya tabel kosong; jalur pemulihan data nyata = fix-forward (docstring baris 22–26). Tes hanya mereverse tabel kosong — sesuai batas terdokumentasi.
- **Record lama tidak bocor ke principal/target salah**: principal dipertahankan apa adanya (protokol lama menyimpan principal pembuat klaim di kolom meski tak dipakai lookup); replay baru hanya cocok principal sama → principal lain mengeksekusi aksi baru miliknya (tes `test_legacy_record_replays_only_same_principal_and_target` dan tes migrasi). Tidak ada jalur yang menyubstitusi principal.
- **Sequencing deploy** (catatan, bukan temuan): kode lama menulis kolom `scope` yang dihapus migrasi; kode baru butuh kolom baru → deploy harus atomic (hentikan worker lama → migrate → jalankan baru); perilaku standar Django — docstring migrasi menyebut kegagalan/ulangi, tidak menyebut sequencing eksplisit.

**REV-INT-004 (P3):** legacy record dengan resource **opaque non-UUID** — khususnya `identity_conflict_resolve` (group_id sha256[:16], protokol lama menyimpannya raw pada bagian resource scope) — masuk cabang `_canonical_uuid → None → delete` (migrasi baris 64–69). Replay kelas itu hilang; klien retry key sama pasca-migrasi mengeksekusi ulang (guard domain `resolve_conflict_group` menyimpan keputusan per discovery-object — re-eksekusi bersifat overwrite). Kebijakan purge masih dalam kelas cache, dapat diterima, namun docstring mengklasifikasikan kelas ini "data rusak" tanpa menyebut kasus opaque token yang justru sah menurut protokol baru (`resource_uuid=False`). Koreksi minimum: catat kasus ini pada docstring/laporan (atau parser khusus untuk operasi resource-opaque bila replay kelas itu dianggap penting).

### E. Kualitas bukti tes — LULUS DENGAN CATATAN

18/18 fungsi tes diverifikasi ada dan asertinya cocok dengan klaim matriks §5 laporan (pembacaan penuh `test_idempotency_pa006.py`, 1057 baris). Yang kuat:
- **Forced interleaving nyata + observasi lock**: `test_concurrent_same_identity_waits_then_replays_single_effect` (611–687), `test_concurrent_same_key_different_body_conflict` (689–743), `test_concurrent_platform_decision_replay_204_single_effect` (745–822): main thread memegang `SELECT ... FOR UPDATE` baris domain → thread A teramati TERBLOKIR pada lock domain; thread B teramati menunggu pada klaim INSERT — **via `pg_stat_activity` dari koneksi observer psycopg terpisah** (`_wait_backend_lock_wait`, 573–586) dengan PID berbeda dibuktikan (`pids["A"] != pids["B"]`). Ini bukan barrier+harapan: kondisi terblokir benar-benar diobservasi sebelum interleaving lanjut. Aserti efek: 1 invoice/1 record, replay identik, audit/outbox/source-event tepat satu, subscription ACTIVE + period_index=1.
- Boundary HTTP memakai klien terautentikasi independen per pengguna (`_client_for`, 123–137 — `CsrfAPIClient` diverifikasi ada di `backend/tests/conftest.py:40`).
- Kegagalan/pemulihan + TTL + legacy + migrasi (forward, dengan fixture skema lama 0003 via `MigrationExecutor`, rollback maju-mundur, verifikasi constraint/kolom via pg_constraint/information_schema) — cakupan setiap baris acceptance packet.

**REV-INT-005 (P3) — batas/kelemahan yang dicatat:**
1. Dua tes konkuren (`test_eight_threads_same_key_no_unique_violation_500`, 824–857; `test_concurrent_different_principal_same_key_both_execute`, 859–894) memakai **barrier saja** tanpa lock-observation — interleaving "dipaksa" hanya oleh serialisasi unique index (memadai untuk jalur klaim, tetapi bukan interleaving dipaksa penuh pada lapisan efek seperti tiga tes lain; packet meminta "bukan hanya barrier lalu berharap race terjadi" — terpenuhi secara keseluruhan oleh tiga tes lock-observation, dua tes ini bersifat stress tambahan).
