## B. Transaction/savepoint correctness — PASS (P3 notes)

1. **Satu transaksi klaim+handler+respons — BENAR.** `idempotency.py:164-186`: `transaction.atomic()` membungkus `IdempotencyKey.objects.create(...)` (claim), `func(...)` (handler), dan `.update(response_status, response_body)`. Jalur tenant: `TenantApiView.dispatch` (common/views.py:101-119) membungkus `_invoke` dalam `tenant_scope` → `transaction.atomic()` + `set_config('app.tenant_id',...,true)` (tenant_context.py:33-53), jadi atomic decorator = savepoint dan COMMIT terjadi bersama di akhir tenant_scope. Jalur platform: `ATOMIC_REQUESTS` tidak diset (settings.py:90, dburl.py:23-37 tanpa opsi isolasi) → atomic decorator adalah transaksi terluar; commit tunggal di akhir blok.
2. **Flag `claim_inserted` — penempatan BENAR.** idempotency.py:171-177: `create(...)` dulu, baru `claim_inserted = True`. Unique-violation klaim terjadi di dalam `create()` → flag tetap False → masuk jalur re-read; IntegrityError bisnis dari handler (flag True) di-re-raise apa adanya (:187-191) → rollback penuh, identik dengan perilaku pra-PA-006. Constraint unique non-deferrable PostgreSQL melaporkan pelanggaran saat INSERT (bukan saat commit), jadi tidak ada jendela "flag salah".
3. **Re-read setelah IntegrityError (jalur tenant) — USABLE.** Savepoint di-roll-back; transaksi tenant_scope luar tetap hidup; GUC `app.tenant_id` dipasang SEBELUM savepoint (dispatch:113-114) sehingga tetap berlaku; `jobs_idempotency_key` TIDAK ber-RLS (jobs/migrations/0002 hanya `enable_rls("jobs_jobdetail")`) sehingga re-read bebas masalah RLS. Isolasi default READ COMMITTED (tidak ada OPTIONS isolasi) → re-read melihat baris yang barusan di-commit pemimpin. Path integritas lain (NOT NULL/null) tidak mungkin pada field yang selalu terisi (`_principal` tidak pernah None; scope ≤ ~74 char).
4. **Jalur platform (atomic terluar) — BENAR.** Rollback penuh lalu `_committed_record` (:108-109) berjalan autocommit sebagai transaksi implisit baru; `set_rollback()` DRF no-op (rest_framework/views.py:66-69 hanya jika `ATOMIC_REQUESTS`); handler platform (`decide_platform_submission`) membuka `tenant_scope` reentrant sebagai savepoint DI DALAM atomic decorator (subscriptions/services.py:409-416) — GUC `is_local=true` ikut ter-roll-back bersama transaksi, tanpa bocor ke koneksi pooled.
5. **Deadlock/starvation — tidak ditemukan deadlock.** Urutan kunci konsisten (claim INSERT dulu, baru kunci bisnis handler); waiter hanya menunggu entry unique index milik leader, tidak ada siklus; purge memakai `FOR UPDATE SKIP LOCKED` (idempotency.py:91-105) sehingga purge konkuren tidak pernah menunggu dan tidak menahan jalur klaim. P3 bawah.

Temuan B:

- **B-P3-1 (latent, saat ini tidak terjangkau): handler yang MENGEMBALIKAN (bukan raise) Response non-2xx akan commit klaim tanpa respons.** Bukti: idempotency.py:178-186 hanya menyimpan respons 2xx; `return response` tanpa exception meng-commit atomic bersama claim → record `response_status NULL` → retry same-body = 409 permanen sampai TTL (:118-122). Saat ini SEMUA 28 handler raise `ApiError` untuk jalur galat dan mengembalikan 200/201/202/204 untuk sukses (diverifikasi satu per satu), jadi jalur ini tak terjangkau — namun tidak ada guard struktural. Koreksi minimal yang disarankan (follow-up, bukan blocker): lewati commit claim untuk response non-2xx (mis. raise/mark-rollback) atau simpan juga status non-2xx sebagai respons logis.
- **B-P3-2: klaim INSERT menunggu tanpa batas waktu bila transaksi leader menggantung.** Tidak ada `lock_timeout`/`statement_timeout` pada DATABASES (dburl.py:23-37). Handler berjalan DI DALAM transaksi (termasuk I/O file `store_payment_proof`); leader yang macat menahan semua retry same-identity sampai transaksinya berakhir. Radius ledakan terbatas (hanya identitas sama; purge SKIP LOCKED tidak ikut terserialisasi). Catat sebagai risiko diterima / kandidat `lock_timeout` pada follow-up.
- **B-P3-3 (race purge-TTL, benign):** purge pesaing bisa memegang lock baris kedaluwarsa saat claim kita menabrak baris itu → IntegrityError → re-read masih melihat baris kedaluwarsa → respons kedaluwarsa sempat di-replay dalam jendela sempit. Semantik aman (masih aksi logis yang sama; TTL adalah retensi best-effort) — catatan saja. Loop `_MAX_CLAIM_ATTEMPTS=2` + 409 fail-safe akhir (:196) menutup kasus baris hilang dua kali.
- **B-P3-4 (informasional):** tidak ada fast-path read sebelum INSERT — setiap replay berurutan membayar satu exception IntegrityError + savepoint. Pilihan insert-first memang pola conflict-safe yang benar; hanya catatan performa.
