## Six findings

1. **P0 — Clean installation cannot pass directory/user creation. IMPLEMENTED but defective.**  
   `instalasi.sh::run` executes `"$@"` directly (`:59–64`), but `create_users_dirs` passes whole shell command strings (`:139,142,144–147`). On a virgin host, Bash attempts an executable named `useradd --system …`; even an existing user cannot bypass the quoted `mkdir -p …` failure. Static syntax checks cannot detect this semantic defect. Additionally, `deploy_backend:238` duplicates dependencies and omits `xhtml2pdf`, required by `backend/pyproject.toml:23` and imported by `domains/documents/rendering.py:29–31`.  
   **Smallest fix:** pass command arguments separately; install from the authoritative dependency manifest. **Acceptance:** disposable Debian 13 clean install and reinstall, verifying application startup, invoice/PDF generation, existing data and secret preservation.

2. **P1 — Upgrade/repair can hide failed gates; repair can remove configured HTTPS. PARTIAL.**  
   `gate_fail` records failure rather than exits (`instalasi.sh:480`); only `summary` maps recorded status to exit codes (`:539–578`). Upgrade and repair never call it (`:635–649,675–676`). Consequently, health failures can finish successfully. `setup_caddy:404,417` uses only the caller’s `MT_DOMAIN`; `repair:647` does not load the persisted environment, so a normal repair without re-exporting the domain rewrites the site to `:80`. Readiness checks only `SELECT 1` (`backend/domains/config/views.py:77–85`), despite its migration-readiness description.  
   **Smallest fix:** consistently load validated persisted configuration, finalize status for every mutating mode, bound health waits, and verify the required schema. **Acceptance:** stopped DB/worker, missing migration and invalid HTTPS produce the documented nonzero status; repair preserves the configured domain.

3. **P1 — Deployment lacks drain/reconciliation and complete worker fencing. PARTIAL.**  
   Upgrade overwrites deployed code and migrates while API/worker remain active (`instalasi.sh:241–250,635–639`). `runworker.py:32–49` has no drain or termination protocol. `engine::run_claimed:227–278` wraps execute/readback in `tenant_scope`, whose `transaction.atomic` spans its body (`tenant_context.py:51–54`), including network/file operations. State transitions, terminal updates and retries write by job ID without checking ownership (`engine.py:213,288,311`); `_fenced_save` is used narrowly and its failure is ignored (`:247`). Expiry reconciliation handles executing/verifying only (`:340–351`).  
   **Smallest fix:** the already identified PA-002 packet: stop claims, finish or safely fence active work, enforce ownership on every effect/state transition, shorten transactions, reconcile before resuming. **Acceptance:** crash/lease-transfer/old-writer and deployment-during-job tests prove no duplicate effect, stale terminal overwrite or stranded claim.

4. **P1 — Platform recovery and secret separation remain incomplete. DOCUMENTED/PARTIAL.**  
   Upgrade produces a local `pg_dump` and checks only archive listing (`instalasi.sh:627–631`); this proves neither restoration nor off-host survival. No executable DB/WAL/blob/key/config recovery workflow was found. Router backup writes simulator manifests (`backups/service.py:118–129,267`), so it supplies no platform DR evidence. CSPRNG generation and key preservation exist (`instalasi.sh:153–192,343–375`), but both runtime services receive an environment containing migrator credentials (`:178,186,285,308`). FreeRADIUS rendering also passes its password through argv (`:456`).  
   **Smallest fix:** separate privileged migration secrets, remove secret argv, implement the released-scope encrypted off-host recovery set and restore sequence in `OPERATIONS.md:44–48`. **Acceptance:** isolated restoration verifies acknowledged financial records, decryptable artifacts, keys, permissions and mutation fencing.

5. **P1 — Actual deployment differs from the approved architecture. DOCUMENTED/PARTIAL.**  
   `ARCHITECTURE.md:27` and `OPERATIONS.md:34–36` require application Compose, native PostgreSQL and separated privileged processes. Installer instead creates native API/worker units under the same OS account/environment (`instalasi.sh:275–319`). No Compose/Docker deployment artifact was found, nor an approving decision in the searched reports. Firewall setup only reports activity/warns (`:327–335`); WireGuard activation remains manual (`:395–396`). Domain directories and handlers provide organizational modularity, but the inspected CI has no import-boundary check (`.github/workflows/ci.yml`).  
   **Smallest fix:** implement the existing architecture, or obtain and record an explicit narrowly scoped native-deployment decision; preserve privilege and network boundaries either way. Add only targeted boundary checks. **Acceptance:** host tests verify permitted process capabilities, peer isolation after reload and restricted service exposure.

6. **P1 — Scheduler, observability and scale evidence cannot support a host-only release claim. DOCUMENTED/UNVERIFIED.**  
   `issue_due_invoices.py:18–19` says the installer configures its 01:00 timer, but repository searches found no timer, `OnCalendar`, installer invocation or scheduler service. Health checks establish process/DB reachability, without the queue/DB-lock/disk/backup-lag observability required by `OPERATIONS.md:38`. The handoff correctly labels 1,000 tenants × 1,000 online clients a design claim (`:115`); the staged profile in `OPERATIONS.md:64–68` uses 300 services/tenant and cannot establish that larger workload.  
   **Smallest fix:** install and monitor the scheduler, expose released-scope operational signals, and correct handoff readiness wording. **Acceptance:** actual timer execution/catch-up produces no duplicate invoices; feature-specific G1/G2/G3 and capacity G4/G5 evidence remains explicit (`ACCEPTANCE.md:44–70`).
