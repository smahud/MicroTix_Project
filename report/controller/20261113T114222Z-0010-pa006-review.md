## 2. Findings and minimum correction

### REV-1311-01 — P1: changed legacy proof scope creates a duplicate submission after upgrade

Maps to SCOPE-002 / RACE-01. `backend/domains/subscriptions/views.py:99–104` changes the retained-key identity from `payment_submission:<tenant>:` to `payment_submission:<tenant>:<invoice>`. `common/idempotency.py:153–194` only claims/looks up the new identity; migration0004 preserves the old rows unchanged. Handler lines113–125 writes another proof and inserts another submission; `subscriptions/models.py:155–190` has no business uniqueness for this logical request.

Concrete flow: a successful old request committed submission S and a nonexpired cached201 under the old scope; the client lost the response. The same principal retries the same invoice/key/body after upgrade. The new decorator ignores the old record and executes again. The result is S2 and two submissions, rather than S and one. Root reproduced this with both a retained-history fixture and an actual main9903d9b HTTP upload → real migration0004 → candidate HTTP retry: **submissions1→2, actual proof files1→2, different submission UUID, both201** ([live upgrade log](../controller-evidence/20261113T114222Z-pa006/live-upgrade-retry.log)). This establishes duplicate payment-proof effects; it does not establish double ledger posting or activation.

Minimum correction: add a narrow, principal- and tenant-safe compatibility/reconciliation policy for identities changed by this patch. Validate any legacy cached submission against its actual actor/tenant/invoice before reuse. Invoice B must never replay invoice A. An ambiguous legacy no-response record must not be treated as permission for a new effect. Preserve history and separate retained-key protection from business uniqueness after TTL. Cover legacy platform/session and UUID-alias shape changes explicitly without blindly replaying foreign data or adding infrastructure.

Closing acceptance: completed and incomplete pre-upgrade records, same owner/invoice/key/body, concurrent retry and actual target B. The successful old action returns its original logical result with one submission/no additional file; changed body conflicts safely; unknown effects are safely reconciled/blocked. Verify real migration/upgrade ordering and preserve unrelated domain state.

### REV-1311-02 — P1: group-only migration scope returns success without applying the target session

Maps to SCOPE-001. `backend/domains/customers/views.py:572–584` scopes `identity_conflict_resolve` only to opaque `group_id`, omitting structured parent `migration_id`. `customers/services.py:572–611` makes group IDs reusable across the tenant; lines637–650 persist decisions for a particular migration session.

Concrete flow: resolve group G for session A with principal P/tenant T/key K/body B. Reuse P/T/K/B for G in session B. Cached204 bypasses `_get_session(B)` and `resolve_conflict_group(B)`, so B receives success with no decisions. Root measured **204/204 with per-session decision counts[2,0]**; malformed and missing parents both returned cached204 instead of422/404. The three authenticated HTTP probes failed their required assertions ([output](../controller-evidence/20261113T114222Z-pa006/probes.log)). This is cross-resource false success within a tenant, not a demonstrated cross-tenant leak.

Minimum correction: include canonical migration/session UUID plus exact opaque group ID in the logical resource. Validate all structured components before replay and handle retained old group-only records safely; preserve string semantics and existing auth/permission checks.

Closing acceptance: HTTP A/B calls using the same group/key/body each create the correct session's decisions; retry A replays; parent UUID aliases identify A; cached G cannot make malformed parent422 or missing parent404 become204. Keep actor/tenant/permission boundaries and existing migration regression intact.

### REV-1311-03 — P2: typed UUID body identities are hashed before canonicalization

Maps to SCOPE-003. `backend/domains/common/idempotency.py:52–54,160` hashes raw body data; `billing/views.py:221–238` subsequently canonicalizes `package_id` before assigning it. A hyphenated UUID and uppercase compact alias refer to the same package but produce different hashes: retrying the same logical key returns409 instead of the original200. Root reproduced **200→409 idempotency_conflict** on the real HTTP handler; no second assignment was claimed ([output](../controller-evidence/20261113T114222Z-pa006/probes.log)).

This is an existing helper gap left unclosed by this submission, rather than a new regression. It is in task0010 mandatory work2 (canonical structured identity before scope/hash), which the executor claims complete. Normalize declared typed identity fields for the relevant active handlers before hashing. Preserve username/password and arbitrary strings exactly, array order and actual changed-body/file409; no generic schema framework or global string transformation is needed.

Closing acceptance: same service/key with equivalent package UUID representations replays200; a different actual package remains409; inspect equivalent declared UUID payload fields and add meaningful targeted tests. Reconcile retained raw-hash records under the same explicit legacy policy.
