## 2. Solusi dan alasan (perubahan minimum)

Defek sumber (packet §bukti masalah, diverifikasi pada baseline):

1. `common/idempotency.py` lama menyimpan `principal` tetapi TIDAK memasukkannya pada scope/lookup/uniqueness (respons bisa ter-replay lintas principal; principal lain terkunci 409 palsu).
2. Klaim `filter().first()` lalu `create()` tanpa reservation conflict-safe → same-key konkuren = unique-violation 500 / efek ganda.
3. Record tanpa respons → eksekusi ulang buta tanpa pembuktian keadaan efek.
4. `payment_submission` tidak menyertakan `invoice_id` (bukti invoice A vs B key sama bertabrakan).
5. Operasi platform mengambil scope dari `request.session["active_tenant_id"]` → berubah saat operator berpindah tenant.
6. Scope raw-text UUID: ejaan alias (huruf besar/tanpa hyphen) target sama → scope berbeda; id malformed → 500 pada endpoint dengan filter mentah.

Perubahan (`backend/domains/common/idempotency.py`, rewrite terfokus):

- **Identity seragam** untuk claim, lookup, uniqueness, update dan replay: `principal + target + operation + resource + key`, dengan `target` = tenant UUID kanonik (dari kwarg route) atau konstanta `platform` untuk route platform (fallback sesi DIHAPUS), dan `resource` dikanonikalisasi UUID (alias bergabung; malformed → 422 `resource_id invalid` — sesuai acceptance packet, tanpa klaim/effect). `resource_is_uuid=False` untuk id opaque non-UUID (group_id konflik identitas = token hex sha256[:16]).
- **Protokol claim/replay satu transaksi**: `INSERT` klaim + eksekusi handler + persistensi respons dalam SATU `transaction.atomic()` (savepoint dalam `tenant_scope` untuk view tenant; transaksi terluar untuk view platform). Pesaing same-identity INSERT menunggu unique index spekulatif PostgreSQL sampai transaksi pemimpin selesai: commit → `IntegrityError` → re-read → replay respons tersimpan; rollback → INSERT pesaing berlanjut → eksekusi segar. `IntegrityError` bisnis dari handler dibedakan via flag `claim_inserted` (set tepat setelah `create()`) dan dibiarkan menggelembung sebagaimana semula.
- **Record tanpa respons** (in-flight pra-PA-006/legacy) TIDAK dieksekusi ulang: 409 `idempotency_conflict` fail-safe (kode kontrak existing); business uniqueness domain tetap penjaga efek; kunci bebas setelah TTL. Tidak ada respons in-progress sementara yang baru dibuat (protokol menunggu lalu replay) — "temporary in-progress response" tidak diperlukan dan tidak diperkenalkan.
- **TTL purge tanpa serialisasi tambahan**: `DELETE ... FOR UPDATE SKIP LOCKED` menggantikan `.delete()` ORM yang bisa menahan kunci baris kedaluwarsa selama transaksi handler berjalan. Semantik retensi 7 hari tidak berubah.

Alternatif yang ditolak: polling/in-progress state kolom baru (tidak perlu — INSERT-wait PostgreSQL sudah membedakan commit/rollback; atomic klaim+respons menutup window "commit tanpa respons"); ON CONFLICT DO NOTHING + marker (kehilangan jaminan satu-transaksi); broker/Redis (dilarang CONTRACT §3).

Model/migration (`backend/domains/jobs/`):

- `models.py` `IdempotencyKey`: `UniqueConstraint(principal, scope, idem_key)` `uq_idem_principal_scope_key` menggantikan `uq_idem_scope_key`.
- `migrations/0004_idem_principal_scope.py`: **AddConstraint(new) dulu, RemoveConstraint(old) kemudian** — uniqueness terjaga sepanjang migrasi; penambahan constraint baru tidak dapat gagal pada data lama ((scope,idem_key) unik ⟹ (principal,scope,idem_key) unik). Kebijakan legacy: baris lama dipertahankan tanpa rewrite; replay hanya mungkin bagi principal sama dengan scope ejaan kanonik sama; baris legacy platform (scope mengikuti tenant sesi lama — defek lama) menjadi tidak terjangkau (arah aman: tidak bocor; mesin state keputusan domain yang menjaga retry); baris tanpa respons → 409 fail-safe sampai TTL. Reverse didokumentasikan fix-forward (reverse bisa gagal bila baris pasca-migrasi lintas-principal telah ada).

Views:
