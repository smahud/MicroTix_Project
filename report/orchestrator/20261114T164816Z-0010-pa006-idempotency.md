## 5. Kebijakan migrasi/recovery (REV-1311-01 dokumentasi wajib)

- **Atomicity**: Django menjalankan satu migrasi PostgreSQL dalam SATU
  transaksi (DDL+DML) — seluruh 0004 (kolom baru → backfill → NOT NULL →
  swap constraint → hapus `scope`) atomik. Kegagalan → rollback penuh,
  skema+data lama utuh. (Koreksi narasi PR17: atomicity bukan
  per-statement.)
- **Write-freeze/drain + ordering old/new-code**: migrasi dijalankan saat
  penulis dihentikan (drain request/stop worker). Kode lama memerlukan
  kolom `scope` (dihapus di akhir migrasi); kode baru memerlukan kolom
  identitas baru — tidak ada window tulis campuran. Migrasi = titik
  write-freeze; setelah sukses nyalakan kode baru.
- **Fix-forward**: kegagalan migrasi → ulangi setelah perbaikan (backfill
  idempoten terhadap baris sudah terisi bila `scope` masih ada). Reverse
  penuh hanya didukung tabel kosong (dev); reverse bersifat lossy
  (normalisasi alias/platform tidak dipulihkan) — jalur pemulihan data
  produksi adalah fix-forward protokol baru.
- **Legacy policy**: tanpa respons → DIPERTAHANKAN (penjaga); platform →
  remap `platform`; opaque group → verbatim (runtime 409); malformed
  3-bagian → dihapus (cache rusak, dihitung); data korup >64 karakter pada
  tenant/resource mentah gagalkan migrasi secara fail-stop atomik (tanpa
  kehilangan parsial; butuh pembersihan manual — dibatasi, tidak dihapus).
- **Retained raw hash**: v2 (normalized) disimpan; perbandingan menerima v1
  raw — body identik byte-per-byte selalu cocok; record v1 dengan body asli
  canonical juga cocok dengan ejaan alias; record v1 dengan body asli
  non-canonical + retry beda ejaan → 409 aman (batas terdokumentasi + tes
  eksplisit, bukan eksekusi kedua).
