## 1. Ringkasan perubahan

PA-006 menutup celah idempotency HTTP pada uang/provisioning/keputusan platform:
identitas klaim kini **principal + tenant/platform canonical + operation + resource
canonical + key**, diklaim secara conflict-safe dalam **satu transaksi protokol**
(claim + efek domain + penyimpanan respons commit bersama), dengan kanonikalisasi
UUID (ejaan alias → satu scope) dan penolakan 422 untuk identitas terstruktur
salah bentuk.

File berubah (semua dalam scope yang diizinkan packet):

1. `backend/domains/common/idempotency.py` — protokol claim/replay baru:
   - identitas lengkap (principal + tenant/platform + operation + resource + key);
     principal dan tenant_platform sebelumnya disimpan/dicari hanya pada
     `(scope, idem_key)` tanpa principal;
   - claim `INSERT … ON CONFLICT ON CONSTRAINT uq_idem_identity DO NOTHING RETURNING id`
     → konkuren same-identity MENUNGGU keputusan transaksi pemilik klaim (tidak
     pernah 500/unique-violation, tidak pernah double-claim);
   - seluruh protokol berjalan dalam `transaction.atomic()` → respons 2xx tersimpan
     DALAM transaksi yang sama dengan efek domain (view tenant: savepoint di dalam
     `tenant_scope`; view platform: transaksi terluar). "Crash setelah commit domain
     sebelum respons tersimpan" tidak lagi dapat terjadi pada jalur ini;
   - exception apa pun (termasuk ApiError) → rollback klaim+efek → retry memakai key
     semula mengeksekusi ulang dengan bersih (§5 "retry hasil tak pasti memakai key
     semula"); respons galat tidak pernah di-cache sebagai sukses;
   - record terkomit tanpa respons (klaim lama ambigu) → ditolak aman 409, tidak
     eksekusi-ulang buta; migrasi 0004 menghapus kelas record ini;
   - `platform=True` → scope eksplisit `platform` (tidak lagi bergeser mengikuti
     sesi active tenant operator);
   - kanonikalisasi UUID (huruf besar/urn/kurang/tanpa hyphen → lowercase canonical);
     resource salah bentuk → 422 `validation_error` sebelum view;
   - `resource_uuid=False` untuk token opaque exact-case (group_id sha256[:16]);
   - HMAC-SHA256 body canonical dipertahankan (rahasia tidak pernah plaintext).
2. `backend/domains/jobs/models.py` — `IdempotencyKey`: kolom identitas
   `tenant_scope`/`operation`/`resource` (canonical), unique constraint
   `uq_idem_identity (principal, tenant_scope, operation, resource, idem_key)`
   menggantikan `uq_idem_scope_key (scope, idem_key)`; kolom `scope` dihapus
   (derivat, dua sumber kebenaran).
3. `backend/domains/jobs/migrations/0004_idempotency_identity.py` — AddField×3,

   RemoveField scope, AddConstraint baru. Kebijakan legacy, rollback, dan

4. `backend/domains/subscriptions/views.py`:

5. `backend/domains/customers/views.py` — `identity_conflict_resolve`:

## 3. Kebijakan migrasi/legacy/rollback (pekerjaan wajib 6)

- **Backfill**: `scope` lama `operation:tenant:resource` diurai deterministic
  (operation tanpa titik dua; tenant UUID atau literal `platform`; resource UUID
  atau kosong) → kolom identitas canonical. Alias (huruf besar dsb.)
  dinormalkan sebelum constraint dipasang. Resource operasi opaque
  (`identity_conflict_resolve` group_id sha256[:16]) dipertahankan verbatim via
  `_OPAQUE_RESOURCE_OPERATIONS` — cermin `resource_uuid=False` pada decorator —
  sehingga record lama kelas itu tetap dapat mereplay pasca-migrasi (koreksi
  review internal REV-INT-004).
- **Purge** (kelas data cache TTL ≤7 hari per §5, BUKAN history bisnis — uang/
  kuitansi/audit tidak tersentuh): (1) record TANPA respons — klaim protokol lama
  yang efeknya tak terbukti (protokol lama commit klaim terpisah dari efek dan
  respons; crash antara keduanya meninggalkan baris ambigu) — dihapus supaya
  tidak menjadi replay-buta ataupun konflik permanen; (2) scope tak terurai; (3)
  duplikat identitas canonical setelah normalisasi alias → dipertahankan record
  TERBARU yang memiliki respons.
- **Ordering**: constraint lama di-dropy setelah backfill (agar kolom scope dapat
  dihapus); constraint baru dipasang setelah backfill menjamin keunikan canonical.
- **Failure/retry**: DDL PostgreSQL atomik per statement; migrasi dapat diulang
  (idempoten terhadap baris yang sudah ter-backfill).
- **Reverse**: memulihkan kolom `scope` dari komponen identitas; CATATAN re-add
  kolom NOT NULL pada tabel berisi baris ditolak PostgreSQL — reverse penuh hanya
  pada tabel kosong (rollback dev); pemulihan data nyata = fix-forward (protokol
  baru). Baris terpurge tidak dibangkitkan kembali (kelas cache, tercatat pada
  output statistik migrasi).
- **RLS/isolasi**: tidak ada pelembesan RLS — jobs_idempotency_key memang tabel
  global tanpa RLS sejak 0001 (isolasi lewat identitas principal pada constraint
  dan filter ORM); tabel tenant lain tidak diubah.

## 4. Distinguish efek DB / persistensi respons / efek eksternal (pekerjaan wajib 7)

- Efek DB + persistensi respons kini SATU transaksi pada jalur aktif (atomic
  protokol); tidak ada lagi jendela "commit domain tanpa respons tersimpan".
- Efek eksternal non-transaksional yang tersisa: (1) berkas bukti pembayaran
  (payment proof) ditulis ke storage sebelum commit — rollback DB meninggalkan
  berkas yatim berpath opaque tanpa referensi (perilaku pra-ada, dilaporkan
  PA-001 sebagai issue terpisah; tidak diperparah oleh PA-006); (2) hasil job
  asynchronous (202) berada di luar protokol HTTP idempotency — dedup outbox dan
  mesin job yang menjaga. Tidak ada klaim exactly-once eksternal dari unique key
  DB: untuk efek lama ambigu (record tanpa respons pra-migrasi) protokol gagal
  aman (409) dan rekonsiliasi eksplisit (mis. operator memulihkan respons sesuai
  outcome) yang dilanjutkan — dibuktikan tes `stuck_claim_without_response…`.

## 7. Keputusan engineering, temuan internal, risiko, NOT_RUN

**Keputusan** (rutin, dalam scope CONTRACT):

1. Respons 2xx saja yang di-cache-replay; kegagalan (exception/ApiError) → rollback
   klaim → retry mengeksekusi ulang. Alasan: §5 "retry hasil tak pasti memakai key
   semula" — menyimpan error 4xx/5xx akan mengubah retry menjadi konflik permanen.
   Respons 204 disimpan (body kosong) dan direplay apa adanya.
2. Pemilih-penunggu (waiter) konkuren: INSERT ON CONFLICT memblok sampai transaksi
   pemilik selesai → penantang langsung mereplay respons (tidak perlu memperkenalkan
   respons "in-progress" sementara baru — kontrak respons tetap stabil).
3. Observasi race pada tes memakai pengamat psycopg terpisah: koneksi Django main
   pada sandbox ini menunjukkan visibilitas `pg_stat_activity` lintas sesi yang
   flaky (kadang baris backend lain tidak terlihat sama sekali, sementara superuser
   selalu melihatnya — dicatat sebagai keanehan sandbox, bukan produk); pengamat
   psycopg stabil 100% pada pengujian berulang.
4. Cleanup TTL tetap di dalam transaksi protokol (urutan statement seragam antar
   request → tidak ada siklus lock → tidak ada deadlock baru).

**Temuan internal / follow-up berbukti (tidak diperbaiki — di luar scope PA-006):**

- `FUP-001` (P2, evidence: `test_uuid_alias_and_malformed_resource_identity`
  catatan): `tenant_id` URL salah bentuk → ValidationError ORM pada
  `resolve_membership` (`domains/common/views.py:37`) → 500, bukan 404/422, pada
  SEMUA endpoint tenant (pra-ada). Koreksi minimum: tangkap ValidationError di
  `resolve_membership` → 404 generik (atau 422) — file di luar scope packet.
- `FUP-002` (P3): berkas bukti yatim saat rollback transaksi upload (pra-ada,
  PA-001 juga mencatat untuk kwitansi).
- `FUP-003` (info): antrean keputusan platform (`_locate_tenant_of_submission`)
  mengiterasi seluruh tenant — sudah tercatat sebagai keputusan beta M2 pada kode;
  PA-006 menambah satu query idempotency per request platform (tabel global, index
  unique langsung) — dampak O(1), namun pola iterasi tetap milik packet lain.

**Risiko/batas:**
